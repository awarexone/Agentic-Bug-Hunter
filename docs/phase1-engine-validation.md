# Phase 1 — Existing Engine Validation

## Summary
`run_agent_hunt()` plus its per-session files (`agent_session.json`, `agent_trace.jsonl`, `agent_bump.txt`) **is the right integration seam**. It is a plain, importable Python function (`agent.py:1653`) that resolves/creates a session directory, persists all state there as JSON/JSONL, exposes a live append-only trace, and reads a bump file for mid-run steering. The desktop shell can drive it by function call and observe progress by tailing the session files, with no need to reimplement engine logic. Two boundaries differ from the assumption, though: the autonomous ReAct loop is **Ollama-only** (the multi-provider `brain.py` is wired to the CLI in `engine.py`, not to `run_agent_hunt()`), and the promised `hunt.py --agent` entry point **does not exist** in `tools/hunt.py`. All evidence in the session/trace is heavily truncated, so full request/response capture must be added by the desktop, not read out of the engine.

## How the engine works today

- **What starts an investigation.** Two independent front doors. (1) The autonomous agent: `agent.py` `main()` (`agent.py:1760`) parses `--target`/`--domain`/`-x` and calls `run_agent_hunt()` (`agent.py:1844`). (2) The interactive CLI: `engine.py` `main()` dispatches subcommands `recon`/`hunt`/`validate`/`report`/`chain`/`chat` (`engine.py:806-819`) to `brain.py`. Note the docstrings in `agent.py:35-37` advertise `hunt.py --target x --agent`, but `tools/hunt.py`'s argparse has **no `--agent` flag** (`tools/hunt.py:776-793`); that invocation path is stale documentation.

- **`run_agent_hunt()` behavior.** Signature at `agent.py:1653-1665`: `run_agent_hunt(domain, *, scope_lock=False, max_urls=100, max_steps=20, time_budget_hours=2.0, cookies="", model=None, resume_session_id=None, use_langgraph=False, scope_checker=None)`. It resolves a session via `hunt._activate_recon_session()` (`agent.py:1674`), builds `HuntMemory` + `ToolDispatcher`, then runs either the LangGraph backend (only if `use_langgraph` and LangGraph is importable, `agent.py:1702`) or the built-in ReAct loop (`agent.py:1729-1748`). Return value is a dict including `domain`, `success`, `model`, `backend` (`"builtin-react"` or `"langgraph"`), `steps`, `completed_steps`, `findings`, `findings_log`, `working_memory`, `verdict`, `session_file`, and (built-in path only) `trace_path` + `bump_path` (`agent.py:1520-1537`, `1750-1752`). Backends: both the built-in ReAct loop (`ReActAgent`, `agent.py:1190`) and LangGraph (`build_langgraph_agent`, `agent.py:1544`) talk to **Ollama only** (`_ollama_lib.Client(host=OLLAMA_HOST)` at `agent.py:1224`; `ChatOllama` at `agent.py:1587`). If Ollama is not installed, `ReActAgent.__init__` raises (`agent.py:1221-1222`).

- **Session persistence.** `HuntMemory` (`agent.py:425`) persists to a single JSON file `agent_session.json` inside the session dir (`agent.py:1680-1681`). `save()` writes `working_memory`, `findings_log` (capped to last `MAX_FINDINGS_LOG=200`), `observation_buf` (last 10), `completed_steps`, `step_count`, `saved_at` (`agent.py:456-466`). `_load()` restores these on construction, silently swallowing any parse error (`agent.py:443-454`) — a corrupt session file resets to empty rather than failing. Sessions live at `recon/<domain>/sessions/<session_id>/` where `session_id` is a timestamp+uuid (`tools/hunt.py:130-131`); `resume_session_id="latest"` picks the lexicographically last dir (`tools/hunt.py:143-144`).

- **Tracing.** `AgentTracer` (`agent.py:1051`) writes append-only JSONL to `agent_trace.jsonl`, line-buffered with an explicit flush per event (`agent.py:1064-1069`), so `tail -f` works live. Event shapes: `tool_call` `{event, step, tool, args}` with args redacted (`agent.py:1079-1081`); `tool_result` `{event, step, tool, elapsed_s, result_preview}` where **`result_preview` is truncated to `result[:400]`** (`agent.py:1083-1085`); plus `loop_warn`, `loop_break`, `bump`, `finding` (`text[:300]`), and `finish` (`agent.py:1087-1101`). Redaction: keys `cookies/cookie/authorization/token/password` are replaced with `"REDACTED"` before writing (`agent.py:1058-1077`).

- **Steering (`agent_bump.txt`).** Read once per ReAct step at the top of `step()` via `_check_bump()` (`agent.py:1305-1316`, called at `1330`). If the file has content, it is injected into working memory as `[OPERATOR GUIDANCE]`, traced as a `bump` event, the loop detector is reset, and **the file is consumed (overwritten with `""`)** so it fires only once (`agent.py:1312`). The CLI can write it via `agent.py --bump SESSION_DIR "message"` (`agent.py:1820-1826`). Cadence is therefore "checked every step, at most one bump consumed per step."

- **Memory.** Four separate stores. `pattern_db.py` (`PatternDB`) — JSONL of successful techniques keyed by `target+vuln_class+technique` (dedup at `memory/pattern_db.py:69-101`), schema `{ts,target,vuln_class,technique,tech_stack,schema_version}` + optionals (`memory/schemas.py:22-24`); `match()` sorts by payout then recency (`memory/pattern_db.py:139-169`). `lead_board.py` — per-target ledger at `memory/leads/<target>.jsonl` (`tools/lead_board.py:34-35`), statuses **`new|investigating|killed|reported|parked`** (`tools/lead_board.py:401`), routes recon signals to `hunt-*` skills via a regex routing table (`tools/lead_board.py:44-120`); re-ingest preserves status. `hunt_journal.py` (`HuntJournal`) — append-only `journal.jsonl` under `hunt-memory/` by default (`memory/hunt_journal.py:63-66`), fcntl-locked writes, schema-validated (`memory/schemas.py:254-302`; actions/results enums at `:48-53`, `:48`). `audit_log.py` — `AuditLog` writes `hunt-memory/audit.jsonl` (one row per outbound request: `{ts,url,method,scope_check,schema_version}` + optionals, `memory/schemas.py:44-46`); same module also holds `RateLimiter` (per-host token intervals, `memory/audit_log.py:117-149`), `CircuitBreaker` (trips after N consecutive failures, cooldown, `memory/audit_log.py:152-201`), `SafeMethodPolicy` (GET/HEAD/OPTIONS safe, others need approval, `memory/audit_log.py:204-237`), and `AutopilotGuard` (see next). All JSONL stores rotate at 10MB keeping 3 backups via `memory/rotation.py`.

- **Scope enforcement.** Enforced at tool-dispatch time, not inside the scanners. `ToolDispatcher.dispatch()` (`agent.py:578`) gates every tool in `NETWORK_TOOLS` (`agent.py:525-530`) through `AutopilotGuard.check_request(method, "https://{domain}")` (`agent.py:632-644`), using real per-tool HTTP methods (`TOOL_METHODS`, `agent.py:536-550`). `AutopilotGuard` check order is scope → circuit breaker → method policy (`memory/audit_log.py:302-356`), scope being a hard block checked first (`:310-321`). **Fail-closed:** if no `ScopeChecker` is supplied, every network request is blocked (`memory/audit_log.py:322-333`; default `fail_closed=True`). `ScopeChecker.is_in_scope(url)` contract (`tools/scope_checker.py:38-87`): returns `True` only if the URL's hostname matches an allowlist pattern (anchored suffix match — `*.target.com` matches `sub.target.com` but not `eviltarget.com` or bare `target.com`; `tools/scope_checker.py:133-147`) and is not excluded; returns `False` for empty/malformed input. **Gap confirmed: IP addresses and CIDR ranges are not supported** — `_is_ip()` detects them and `is_in_scope()` returns `False` with a stderr warning (`tools/scope_checker.py:66-72`, `149-161`); there is no CIDR handling anywhere in the class. Extra hardening: recon output files are filtered in place to scope before scanners read them (`agent.py:794-837`), and `run_sqlmap_on_file` parses the `Host:` header out of the request file and blocks out-of-scope hosts before running (`agent.py:615-630`).

- **Findings representation.** In-memory list `findings_log` of dicts `{tool, severity, text, ts}` with **`text` truncated to 500 chars** (`agent.py:479-485`). Findings are auto-classified from observation text by keyword matching into CRITICAL/HIGH/MEDIUM/LOW (`_classify_obs`, `agent.py:983-1002`) — this is heuristic, not structured scanner output. Stored in `agent_session.json` (capped at 200). There is **no full request/response body stored anywhere** — observations are truncated to `MAX_OBS_CHARS=3000` (`agent.py:123`, `:473`), trace previews to 400 chars, finding text to 300–500 chars. Raw scanner artifacts do exist on disk under `recon/<domain>/` and `findings/<domain>/`, which the dispatcher summarizes (`agent.py:841-981`), but the agent's own record of them is lossy.

- **Validation (`tools/validate.py`).** This is the interactive **4-gate** checklist (Gate 1 "Is it real?" incl. cross-account identity check, Gate 2 "In scope", Gate 3 "Exploitable" requiring a real curl PoC, Gate 4 "Not a dup" with a live HackerOne GraphQL query) — `tools/validate.py:301-502`. (The "7-Question Gate" branding lives in the `report`/`triage` LLM path, `brain.triage_finding()`, `brain.py:1721`, and in skill docs — a separate thing.) Input: interactive prompts + flags `--program`, `--scanner-summary`, `--scanner-confidence` (`tools/validate.py:854-870`). It computes an approximate CVSS 4.0 score from a lookup table (`tools/validate.py:94-129`). Output: writes `hackerone-report.md` skeleton, `submission-notes.md`, and a structured `validation.json` (status `validated_finding` vs `scanner_hit`, per-gate notes, rejection reasons) into `findings/<program>-<vuln>/` (`tools/validate.py:950-979`, `782-849`); it is **stdin/tty-driven**, not a callable API returning a value.

- **Report generation.** Three mechanisms, all present: (1) LLM-written reports via `Brain.write_report()` (`brain.py:1601`), which builds grounded evidence, prompts the model for the top-3 findings in a fixed H1-style format (`brain.py:1615-1667`), post-processes for hallucinations (`_ground_report_output`), and saves to `findings/<dir>/04_h1_reports.md`; invoked by `engine.py report` (`engine.py:535`). (2) The `validate.py` skeleton generator above. (3) Static markdown **templates for all four platforms** in `skills/report-writing/SKILL.md` — HackerOne (`:72`), Bugcrowd (`:148`), Intigriti (`:185`), Immunefi (`:247`) — consumed by the agent/`report-writer` sub-agent as guidance, not by code. There is no programmatic template engine that fills these four per-platform templates from a finding object.

- **Provider detection (`brain.py`).** `LLMClient` precedence (`brain.py:222-233`, `255-272`): explicit `BRAIN_PROVIDER` env wins; otherwise `_auto_detect()` front-loads any provider whose API-key env var is set (`PROVIDER_KEY_ENV`, `brain.py:236-252`), then falls through `PROVIDER_PRIORITY` (ollama, groq, deepseek, cerebras, gemini, kimi, mistral, together, perplexity, orcarouter, openrouter, claude, openai, grok — `brain.py:181-185`), with Ollama as the final fallback (`brain.py:272`). Keys are read from env vars listed at `brain.py:20-36` / `237-252` (e.g. `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GROQ_API_KEY`, `OLLAMA_HOST`). Model selection: `BRAIN_MODEL` forces one; for Ollama, `_pick_model()` walks `MODEL_PRIORITY` (`brain.py:692-707`, `793-815`) and an explicit-but-missing model fails rather than silently substituting (`brain.py:807-808`). **Important:** this multi-provider layer is only used by `engine.py`/CLI phases; `run_agent_hunt()` performs all inference against Ollama and is hard-bound to it. The only `brain` touch on the agent path is optional model-*name* selection: the LangGraph branch calls brain's `_pick_model()` when `_BRAIN_OK` (`agent.py:1704`). No `LLMClient` is ever instantiated for inference in the agent path.

- **CLI (`engine.py`) and GUI-reusability.** `engine.py` is a standalone argparse CLI providing `setup` (interactive provider/model wizard), `providers`, `models`, `status`, `chat`, `recon`, `hunt`, `validate`, `triage`, `report`, `chain`, `mcp` (`engine.py:806-819`). It is **terminal-oriented**: `setup`/`chat`/`validate` use `input()`/stdin (`engine.py:255`, `594`, `670-680`), and most commands print colorized output rather than returning data. It is **not directly GUI-reusable as-is**, but its building blocks are: the underlying `Brain` methods (`analyze_recon`, `interpret_scan`, `write_report`, `build_chains`, `triage_finding`) and helpers like `load_config`/`save_config` (`engine.py:83-97`) are importable and return strings. A desktop would call those, not shell out to `engine.py`.

- **On-disk data locations.** Runtime artifacts (repo-root relative in both `engine.py:53-58` and `tools/hunt.py:88-93`): recon under `recon/<domain>/` (agent sessions at `recon/<domain>/sessions/<id>/` holding `agent_session.json`, `agent_trace.jsonl`, `agent_bump.txt`), findings under `findings/<domain>/`, reports under `reports/<domain>/`. Hunt memory: `hunt-memory/journal.jsonl`, `hunt-memory/patterns.jsonl`, `hunt-memory/audit.jsonl` by default, overridable via `BBHUNT_MEMORY_DIR` (`tools/validate.py:804`, `memory/hunt_journal.py:63-66`). Lead board: **separately** at `memory/leads/<target>.jsonl` under the repo (`tools/lead_board.py:34-35`) — a different root than the other memory files. Config + API keys: `~/.bughunter/config.json`, written `chmod 0600`, containing provider, per-provider model map, and **plaintext API keys** (`engine.py:58`, `94-97`, `267-287`).

## Existing capability
- A clean, importable autonomous hunt entry point (`run_agent_hunt()`) that returns a structured result dict and persists everything to a predictable session directory.
- Live-observable progress: append-only, immediately-flushed `agent_trace.jsonl` (tailable) and a resumable `agent_session.json`.
- Mid-run operator steering via `agent_bump.txt` (write-once-per-step semantics).
- Deterministic, fail-closed scope enforcement at dispatch with anchored subdomain matching, plus recon-file scope filtering and request-file host blocking.
- Defense-in-depth request guards: circuit breaker, per-host rate limiter, safe-method policy, and an append-only audit log — all schema-validated with size-based rotation.
- Session resume by id or `"latest"` (`tools/hunt.py:119-153`).
- Cross-target learning stores (pattern DB, hunt journal) and a lead ledger that routes recon signals to skills and tracks per-lead status.
- A multi-provider LLM abstraction (14 providers) with env-based auto-detection — usable for CLI phases and report/triage.
- Interactive 4-gate validation with approximate CVSS 4.0 and H1 skeleton output; per-platform report templates (H1/Bugcrowd/Intigriti/Immunefi) and LLM report writer with anti-hallucination grounding.
- Secret redaction of cookies/tokens/passwords in the trace.

## Missing capability
- **Full request/response evidence capture.** Everything the agent records is truncated (observations 3000 chars, trace preview 400, findings 300–500). The desktop needs its own evidence store (raw request/response pairs, screenshots) — tie to the plan's evidence/capture phase.
- **Multi-provider support for the autonomous agent.** `run_agent_hunt()` is Ollama-only; cloud providers only work through the CLI/`Brain`. If the desktop MVP must run without a local model, this requires wiring `brain.LLMClient` into the ReAct loop — tie to the provider/settings phase.
- **A real headless control API.** There is no local daemon/HTTP/IPC surface; the only programmatic seam is calling `run_agent_hunt()` in-process. The desktop needs a thin control layer (start/stop/status/bump) — tie to the backend/bridge phase.
- **Structured findings model.** Findings are keyword-classified free text, not typed records with request/response/CVSS/status. A proper finding schema + store is needed — tie to the findings/data-model phase.
- **IP/CIDR scope support.** `ScopeChecker` explicitly rejects IPs and has no CIDR logic; any IP-scoped program is unsupported — tie to the scope phase.
- **Keychain / secure secrets.** API keys sit in plaintext `~/.bughunter/config.json`; the desktop should move these to macOS Keychain — tie to the secrets/security phase.
- **SQLite (or any) index over sessions/findings/memory.** Current storage is scattered JSON/JSONL across `recon/`, `findings/`, `hunt-memory/`, and `memory/leads/`; there is no queryable index for a UI list/detail view — tie to the persistence/index phase.
- **A stable `hunt.py --agent` (or equivalent) entry.** Documented but absent; the desktop should call `run_agent_hunt()` directly and not rely on that flag.
- **Non-interactive validation.** `validate.py` is tty/stdin-bound; a desktop needs a callable validation function returning structured results — tie to the validation-integration phase.

## Integration boundary
Connect at the **function-call seam `agent.run_agent_hunt(...)`**, passing a pre-built `ScopeChecker` (never rely on the fail-closed default silently) and explicit `model`/`time_budget_hours`/`max_steps`. For live UI, **read the per-session files** the function creates: tail `agent_trace.jsonl` for events, poll `agent_session.json` for findings/working memory, and **write** `agent_bump.txt` for steering (respecting its consume-on-read behavior). For validation/report/triage, call `Brain` methods (`brain.py`) directly rather than shelling `engine.py`. The desktop must **not**: reimplement the ReAct loop, tool dispatch, or scope logic; write into `agent_session.json`/`agent_trace.jsonl` (owned by the engine — treat as read-only, bump file is the only write channel); duplicate the scanner orchestration in `tools/hunt.py`; or invent its own scope matcher — extend `ScopeChecker` in place for IP/CIDR instead. Session directory layout (`recon/<domain>/sessions/<id>/`) and memory paths should be treated as the engine's contract and not relocated without changing the engine.

## Risks
1. **(High) Autonomous agent is Ollama-only.** `run_agent_hunt()` performs all inference against a local Ollama model (`agent.py:1223`, `1587`); the multi-provider `brain.py` is only touched for optional model-name selection on the LangGraph branch (`agent.py:1704`), never for inference. If the desktop MVP assumed cloud providers "just work" for hunting, that is false — this changes provider/settings scope significantly.
2. **(High) Plaintext API keys on disk.** `~/.bughunter/config.json` stores keys in cleartext (`engine.py:94-97`, `267-283`); `0600` perms are the only protection. Shipping a desktop app that persists here without Keychain is a real secret-exposure risk.
3. **(High) Evidence provenance is weaker than assumed.** All findings/observations/trace entries are truncated and findings are keyword-heuristic, not verified scanner records (`agent.py:479-485`, `983-1002`, `1083-1085`). Any "evidence" surfaced from the trace is a preview, not proof — the desktop cannot rely on it for reports.
4. **(Medium) Scope gap: no IP/CIDR.** `ScopeChecker` fails closed on IPs (`tools/scope_checker.py:66-72`) — IP-scoped programs are entirely unsupported, and because it fails closed, such hunts will silently block every request rather than error clearly at setup.
5. **(Medium) Stale/absent entry point.** `hunt.py --agent` is documented (`agent.py:35-37`) but not implemented (`tools/hunt.py:776-793`); building against it would fail. Also `use_langgraph` silently falls back to the built-in loop on any error (`agent.py:1726-1727`), so the reported `backend` can differ from what was requested.
6. **(Medium) Resume/session fragility.** `HuntMemory._load()` swallows all exceptions and resets to empty on a corrupt `agent_session.json` (`agent.py:443-454`); `"latest"` resume depends on lexicographic dir sort (`tools/hunt.py:143-144`). Concurrent runs on the same domain could interleave, and there is no lock on the session file.
7. **(Medium) Provider "no-refusal" system prompts.** `BRAIN_SYSTEM` (`brain.py:733-774`) and `AGENT_SYSTEM` instruct the model never to refuse or add safety caveats. Hosted providers (Claude/OpenAI) may still refuse or moderate, producing empty/short outputs (`.chat()` returns `""` on error, `brain.py:498-506`) that the UI must handle gracefully.
8. **(Medium) Split memory roots, asymmetric CWD-sensitivity.** `recon/`, `findings/`, `reports/`, and `memory/leads/` are repo-anchored via `__file__` (`tools/hunt.py:88-93`, `tools/lead_board.py:34-35`), but journal/patterns/audit default to a **CWD-relative** `Path("hunt-memory")` (`memory/hunt_journal.py:65`; also `mcp/bughunter-mcp/adapters.py:243`). A desktop launched from an arbitrary working directory will write memory to a different place than sessions/leads. Treat pinning `BBHUNT_MEMORY_DIR` (and an explicit run root) as a hard requirement, not a nicety.
9. **(High) No cooperative cancellation.** `run_agent_hunt()` runs in-process and blocking; the time-budget gate only refuses to *start* a new network tool under ~10% remaining (`agent.py:585-599`), and an already-launched scanner can overrun by its own timeout (recon up to ~3600s, vuln scan up to ~1800s). A desktop "Stop" button cannot truly halt an active hunt — only kill the sidecar process or wait. The backend/bridge phase must design Stop as process-kill + safe cleanup, not a graceful in-loop cancel.
10. **(Medium) Hard dependency on external scanner binaries.** The dispatcher shells out to nuclei/sqlmap/etc. via `tools/hunt.py`; in a packaged desktop app these may be absent, so `NETWORK_TOOLS` returns error text instead of findings. Packaging must include a preflight/tool-availability check or the MVP's "it just hunts" expectation breaks silently.
